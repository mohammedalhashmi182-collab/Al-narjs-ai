# Al-Narjis service-company pilot: evidence and gates

Assessment base: `192c92d13c2d43e3f0507ae3c417761df7f924f3` (main). This is a code and local-test assessment, not evidence that a feature is configured or functioning in production. No actual customer, payment, provider account or outbound message was used.

## Candidate pilot

Data-to-Deck DocPack: the customer supplies a brief and/or CSV/XLSX data, and receives a requested PDF/XLSX/PPTX/DOCX package. Existing generation and file-opening tests make this a technically concrete first candidate, not an approved new commercial product. The package prices in `src/services/catalog.py` are subscription prices, not an approved standalone DocPack service price. Do not create or send a paid offer until the owner approves service scope, catalog price, duration, revision count and refund terms. A fictitious zero-price test fixture is not a commercial offer.

## Current branch: concrete change and limitations

When `docs/drafts/docpack-project-isolation.patch` is applied, project and owner DocPack outputs require the owner or the originating active project's valid portal session; revoked, anonymous and other-project sessions receive the same 404 as an unknown file. Explicit demo outputs are still short-lived public bearer links, including user-supplied demo inputs; demo is unsuitable for sensitive customer data. The patch was applied and tested in a local worktree, but is **not applied to the remote branch**: the connected GitHub tool rejected the 176 KB `src/main.py` update at its 64 KiB input limit. The remote branch contains only this assessment and the patch; do not merge it as an implementation. Apply and review the patch with an authenticated development tool, then rerun all tests. No database migration, real API, paid transaction, messaging, branch merge or deploy is included. Storage remains process-local and ephemeral. Email attachment behavior and missing mandatory QA are **not fixed by this change**, so this change is not sufficient for production delivery or pilot completion.

## Integration plan and test gates

1. Approve the pilot's commercial scope/price/terms separately; keep a sandbox-only fixture before approval. Define canonical identity and consent; use existing CRM/catalog/project/payment models where suitable and propose any data-model changes for review **before** applying a migration.
2. Add immutable accepted offer and order links, tenant-scoped activity log and deterministic state transitions. Project activation alone is not a service fulfillment proof. Payment provider sandbox verification must match actual provider account, environment, expected amount/currency/reference/recipient; no secrets in repo.
3. Add a transactional durable work queue/outbox plus leased jobs and idempotency keys for provider events, generation and every external side effect. Resume safely after crashes and handle simultaneous delivery. Preserve evidence of attempted and confirmed operations separately.
4. Add mandatory fail-closed QA and durable artifact storage, authorize each download, limit and log access, and remove unreviewed delivery. Only a verified tool result is evidence an external action happened. Implement customer revision and support flow and owner dashboard after safe state transitions are available.
5. Run isolated integration tests with synthetic identities/data and a **documented real provider sandbox transaction** (not live money); only if sandbox credentials/account are separately available. Include declined/mismatched payment, invalid signature, duplicate/concurrent events, insufficient input, worker crash/restart, failed QA and recovery, access revocation, cross-tenant denial, revision and satisfaction. Report which were actually run; mocks alone are not a provider-confirmed sandbox transaction.

**Stop gate:** Do not generalize the service catalog or claim an autonomous company until the complete pilot and above failure tests pass. Do not merge or deploy without explicit owner approval.
